Level: Architect · Module 64: Keeping what matters in long conversations · Page 2 of 2 Exams: A5.1; S1

After this page you can trim a long history with a window that keeps tool calls whole, combine recent turns with a structured summary, decide what a returning customer's stored facts are worth, apply an update that arrives mid-conversation, and keep one customer's facts out of another customer's context, and you can write the module's practice.

Checked on 2026-10-04 against the exam guide's task statement 5.1 and the scenario S1 description, against the Claude API documentation on context editing, compaction and the memory tool as module 29 summarises them, and against the Claude API's handling of tool results (a result must follow the call that produced it). Nothing here called a model: the practice is graded by Python, TypeScript, Java and Kotlin test suites, offline, on messages and facts written by hand. The outline of this module also names the effects of a returning user's stale data and of updates that arrive mid-conversation. The guide's task statement does not use those words; they are the practical form of "preserve critical information across long interactions", and the exam can ask them inside scenario S1.

Exam guide and current product. What the guide states, and so what the exam keys: task statement 5.1 pairs the case facts block with a separate context layer for structured issue data in multi-issue sessions. It does not say how a store is keyed, and the exam's isolation questions rest on the practice described below. What the product offers now (documentation as read for module 29 on 2026-10-03, rechecked 2026-10-04): context editing can clear old tool results by rule, server-side compaction replaces older turns with a summary, and the memory tool keeps files outside the context window across sessions, with the application deciding where they live. None of these is a customer boundary: the product gives mechanisms, and the application decides which customer's facts a request may contain. On the exam, a question about one customer seeing another's data has the answer: scope the store by the authenticated customer and build the context from it in code, never from the model's own text and never by an instruction in the prompt.

Why it matters

The agent from the first page now has the facts block. A new set of problems appears with time. The conversation reaches the window and something must go: which messages? The customer comes back after nine days and the block says the parcel is "out for delivery": is that still true? Mid-conversation the customer says the address has changed, and a delayed copy of the old message is processed afterwards: which address wins? And one process serves thousands of customers: what stops customer B's facts from landing in customer A's request? These are the questions of S1 at scale.

The idea

A window that keeps tool calls whole

When the history must shrink, the cheapest method is a window: keep the newest turns that fit the budget and drop the oldest. Two rules keep it valid. The unit to drop is the exchange, not the message: a tool call and its result stay together or go together, because a result with no call (or a call with no result) is an invalid conversation that the API refuses. And the window is one unbroken run from the newest message backwards: it stops at the first unit that does not fit and does not skip over it to keep an older, smaller one, since a hole in the middle of a conversation is worse than a shorter conversation. The practice's window does both, with tokens estimated as length over four.

A window forgets. So it is paired with the two mechanisms of the first page: the case facts block carries the numbers, and a structured summary of the dropped turns carries the story: decisions made, questions still open, identifiers in play. Recent turns are kept verbatim; older turns exist as structure. Server-side compaction and the clearing of old tool results (module 29) do part of this work for you. They do not change the rule, since what the facts block holds must be rebuilt into the request whatever the platform summarised.

Facts have an age

A fact has a date, and the date decides. A value with the same or a later date replaces the stored one, which moves to the history; a value with an earlier date is recorded in the history and does not replace anything. Order of arrival does not decide: a delayed message that carries an old address must not undo a new one. The old value is kept in the history, since an audit or a dispute may ask what was known when. update_facts implements that, and it returns a new map and leaves its input alone, so that a failed step cannot leave half an update behind.

A returning customer is the same problem across a longer gap. The facts in the block were true on the day they were read, and the world moved. A policy has a freshness limit for each kind of fact (a delivery status is stale in hours, a shipping address in months). A fact older than its limit is read again from the system of record before the agent acts on it, and the agent says which date it is going by. The example's stale is the one-line test. What the agent must not do is act on the stored value because "facts outrank guesses": a stale fact is a guess with a date on it.

Interleaved issues belong here too. A customer raises a late parcel, then a billing error, then returns to the parcel, so no issue's entry is dropped until the case closes.

One customer, one scope

The worst failure of a long-lived system is a context that contains another customer's data. It is a design question about scope: a conversation is bound to one customer when it starts, from the authenticated session, and everything that enters the context is read by that identity. Four rules follow.

  • The facts are looked up by the session's customer id, which the application holds. An id taken from the model's text, a user message or a tool argument that the model filled in can be wrong or forged, and a wrong id loads the wrong customer.
  • The context is built by code that filters on the id, as build_context does: facts of other customers are excluded where the text is assembled, not left for the model to ignore.
  • A rule written in the prompt is not isolation. "Never mention another customer's data" asks the model to ignore text that is already in front of it, and a model that sees the data can use it.
  • Everything that is cached, remembered or summarised is scoped the same way: a memory directory per customer, a cache entry per conversation, a summary stored under the customer's id. A shared store keyed by a common name (preferences) is a leak waiting for two customers who use the name.

The practice: a context for a long support session

The practice is in exercises/64-keeping-what-matters-in-long-conversations. You write the trimming of a tool record, the update of case facts, the assembly of a context for one customer, the check of a summary against the facts, and the sliding window. It is graded in Python, TypeScript, Java and Kotlin; the statement lists eight cases, each saying what you should see when it works.

Traps

  1. "A delayed message arrived last, so its address is the current one." It is tempting because the newest write usually wins. The exam rejects it: the fact's date decides, and a late older value goes into the history without replacing the current one.
  2. "The customer's data is in the facts block, so it is right." It is tempting because the block is structured. The exam rejects it: the block is as old as the day it was read, and a value past its freshness limit is read again before the agent acts.
  3. "Tell the model never to mention other customers' data." It is tempting because the instruction is one line. The exam rejects it: data that is in the request can be used whatever the prompt says. Keep it out of the request by scoping the store and filtering where the context is built.
  4. "Look the facts up by the customer id that the model mentions." It is tempting because the model has just read the customer's message. The exam rejects it: the id comes from the authenticated session, since an id in the model's text can be wrong or planted.

Module quiz

This quiz covers both pages of the module.

  1. Scenario S1, customer support resolution agent. A customer returns after nine days. The facts block says the parcel is out for delivery, a state that the team treats as stale after a few hours. What should the agent do before replying?
    • a: Answer from the block, because stored facts outrank guesses
    • b: Ask the customer what the status was when they last looked
    • c: Read the value again from the order system and say which date applies
    • d: Discard every stored fact and rebuild the case from the customer's messages
  2. Scenario S3, multi-agent research system. A synthesis agent receives forty findings from subagents as one long text, and its report leaves out findings from the middle of that text. Which change fits best?
    • a: Ask each subagent for longer explanations so that every finding takes more room
    • b: Open with a short digest of key points, then group detail under headers
    • c: Send the same forty findings twice so that each one appears in two places
    • d: Sort the findings alphabetically before they are joined into the input
  3. Scenario S1, customer support resolution agent. A customer raises a late parcel and a billing error in one chat, each carrying a different sum, and later returns to the parcel. The agent mixes the sums. Which structure fits?
    • a: A single running total of the sums that spans both matters at once
    • b: One summary sentence that covers both matters and their sums
    • c: Dropping the first matter's data as soon as the second matter begins
    • d: A separate entry per matter with figures and dates, kept to closure
Answer key
  1. c. A fact past its freshness limit is read again from the system of record, and the agent states the date it is going by. a is ruled out because "a stale fact is a guess with a date on it". b is ruled out because the remedy is to read the value again "from the system of record", not to ask the customer to recall it. d is ruled out because the facts are valid until their limit, and the block is how the numbers survive: "the case facts block carries the numbers".
  2. b. Key findings go first under a header, with the detail under explicit headers. a is ruled out because "the middle is where findings go missing", and longer text makes the middle longer. c is ruled out because the guide's remedy is placement: "Put the key findings and the case facts at the beginning of the aggregated input". d is ruled out because ordering by name changes nothing about where a finding sits: "Organise the detail under explicit headers".
  3. d. Each matter has its own entry, and no entry is dropped until the case closes. a is ruled out because "each issue has its own entry in the block, so that two refunds in one conversation never share an amount". b is ruled out because "A reader of the summary cannot tell that anything was lost". c is ruled out because "no issue's entry is dropped until the case closes".

Problem statement

Practice: a context that keeps the facts, trims the noise, never mixes customers and never splits a tool call

A support agent works with a customer over many turns. Its summaries turn "$129.50 by 30 September" into "a refund soon", every order lookup drops forty internal fields into the conversation, a late message with an old address overwrites the new one, a facts block loaded for one customer shows up in another customer's session, and the window that trims old messages sometimes keeps a tool result without the call that produced it. In this practice you write the context's building blocks: the trimming of a tool record, the update of case facts, the assembly of the context, the check of a summary against the facts, and the sliding window. The model is not called. It is in Python, TypeScript, Java and Kotlin;

Names are Python's (trim_record, update_facts, build_context, missing_from_summary, window); TypeScript has the camel-case names (trimRecord, ...); Java has the same camel-case names as static methods of ContextBuilder with the records the starter defines (Fact, FactEntry, Message); Kotlin has top-level functions and the same data classes. A token is estimated as the length of the text divided by four, rounded up (estimate_tokens, given).

What is already written, and what you write

The starter is a working context builder with six gaps cut out of it. Everything that is plumbing is written and correct: the token estimate, the copy of the facts before a change, the new-fact case, the summary and recent-messages sections, the join of the sections and the cost loop of the window. Each gap is marked TODO k of N with a comment that says what it receives and returns, with one example, and the cases it unlocks. A gap leaves a neutral value (nothing added, an empty list, null, the unchanged input), so the starter runs and fails the cases on an assertion. To debug a gap, log its input with the log line at the top of the file: a run shows the logged lines under the failing case. Write the gaps in this order (the TypeScript, Java and Kotlin names are the camel-case forms where a name is given):

  1. The trimmed record (unlocks m1, e1): only the named fields are kept, with their exact values and in the order they are named; a named field the record does not have is skipped.
  2. The newer fact (unlocks e2, e3): a fact that is as new as the stored one or newer replaces it and the replaced value is kept in superseded as value@date; an older fact that arrives late is only added to the history and does not replace the current value.
  3. The customer's facts (unlocks e4): only the case facts of the customer the context is built for are used; those of another customer never enter it.
  4. The case facts section (unlocks e5): when the customer has facts, a ## Case facts section with one line name: value (as of date) each comes first, before the summary and the recent messages.
  5. The values the summary lost (unlocks e6): the names of the facts whose exact value does not appear in the summary are returned, so a summary that lost a value is reported.
  6. The tool call with its result (unlocks e7): a tool call and the result that follows it with the same id form one unit that the window keeps or drops whole; every other message is a unit of its own.

m1 needs gap 1. About sixteen lines in all. The steps below describe the whole builder, so you can see how your gaps are used.

What to write

  • trim_record(record, keep) returns a new record with only the fields named in keep, in the order of keep, with their values unchanged. A name the record does not have is skipped.
  • update_facts(facts, name, value, as_of) returns a new facts map (the input is not changed). A fact is {value, as_of, superseded} where as_of is an ISO date and superseded is a list of "<value>@<date>" strings. A new name is added with an empty history. When as_of is the same as or later than the stored one, the new value replaces the stored one and the old one is appended to the history. When it is earlier, the stored value stays and the late value goes into the history.
  • build_context(customer, facts, summary, recent) takes fact entries {customer, name, value, as_of}, the summary text and the recent messages (role, text). It returns the text: ## Case facts with one line <name>: <value> (as of <date>) for each fact of this customer only, in the given order (the section is left out when the customer has none), a blank line, ## Summary so far with the summary, a blank line, and ## Recent messages with one line <role>: <text> for each message.
  • missing_from_summary(summary, facts) returns the names of the fact entries whose value does not appear verbatim in the summary, in order.
  • window(messages, budget) takes messages {role, kind, id, text} where kind is text, tool_use or tool_result. It returns the newest messages, in their original order, whose estimated tokens add up to the budget at most. A tool call (a tool_use immediately followed by the tool_result with the same id) is kept whole or dropped whole. The window is one unbroken run from the newest message back: it stops at the first unit that does not fit.

Why each part is there, and what you should see

  1. Trim before the context fills. A lookup with forty fields costs tokens on every later turn although five fields matter. You should see only the named fields, exactly as returned.
  2. Newer information wins, history stays. A customer's address changes mid-conversation, and a delayed older message must not undo it. You should see the new value current, the old one in the history, and a late older value recorded without replacing anything.
  3. Scope isolation. A facts block is loaded for one customer's session. You should see another customer's facts absent from the text.
  4. Position and headings. The facts come first, under a heading, so that they are not lost in the middle of a long input. You should see the three sections in that order.
  5. Summaries lose numbers. An exact amount or date that a summary rounds off is a defect that no reader notices. You should see the names of the facts the summary no longer holds.
  6. A window that respects tool calls. A tool result without its call is not a valid conversation. You should see a call and its result kept together or dropped together.

It returns the newest messages, in their original order, whose estimated tokens add up to the budget at most. A tool call (a tool_use immediately followed by the tool_result with the same id) is kept whole or dropped whole. The window is one unbroken run from the newest message back: it stops at the first unit that does not fit.


Why each part is there, and what you should see


  1. Trim before the context fills. A lookup with forty fields costs tokens on every later turn although five fields matter. You should see only the named fields, exactly as returned.
  2. Newer information wins, history stays. A customer's address changes mid-conversation, and a delayed older message must not undo it. You should see the new value current, the old one in the history, and a late older value recorded without replacing anything.
  3. Scope isolation. A facts block is loaded for one customer's session. You should see another customer's facts absent from the text.
  4. Position and headings. The facts come first, under a heading, so that they are not lost in the middle of a long input. You should see the three sections in that order.
  5. Summaries lose numbers. An exact amount or date that a summary rounds off is a defect that no reader notices. You should see the names of the facts the summary no longer holds.
  6. A window that respects tool calls. A tool result without its call is not a valid conversation. You should see a call and its result kept together or dropped together.
